PyPSA-SPICE web application

This guide maps the React, TypeScript, FastAPI, and filesystem code. It shows which module owns each job, how requests move through the app, and where to make a change.

Overview

The web workspace has two local layers. The browser handles interaction and unsaved editing state. FastAPI handles discovery, validation, file access, and process control. Model files under data/ remain authoritative. The app has no database or second model-data format.

Browser

React workspace

Chooses project and scenario context, renders editors and charts, keeps unsaved drafts, and calls typed API helpers.

Server

FastAPI boundary

Validates query and body data, confines filesystem paths, serialises responses, and coordinates edits and model runs.

Repository

Model source of truth

The backend updates CSV and YAML inputs atomically. It does not change result CSVs. Snakemake reads a run-local copy of base_config.yaml.

Design boundary. pypsa_spice_web/ is independent of the legacy Streamlit visualisation. Consult Streamlit for data semantics only. Do not use its structure, components, styling, or interactions as web UI references.

Runtime request flow

User-visible data follows one dependency direction. React components never read repository files, and backend domain modules do not depend on React.

1. User actionChoose context, edit a cell, open a chart, or start a run.
2. React componentOwns view state and invokes an API helper.
3. api.tsBuilds request parameters and normalises HTTP errors.
4. FastAPI routeValidates the HTTP contract and delegates domain work.
5. Local resourcesCSV, YAML, result folders, Git metadata, or Snakemake.
Response path. Domain functions return JSON-safe dictionaries. FastAPI sends them to the browser, then React updates component state and renders. React ignores an aborted read after the user changes context.

Frontend logic

Shared application state

  • view selects Home, Inputs, Scenario differences, Configure & run, Results, or Dashboards.
  • selection holds the Results dataset, project, result run, comparison run, sector, and year.
  • inputSelection holds the editable input dataset, project, and scenario.
  • The URL records durable context so refresh and browser history can restore the workspace.

Local page state

  • Editors own unsaved drafts and register through utility.tsx.
  • Chart cards own filters, time range, request state, and loaded rows.
  • Dashboard definitions are browser-local; fetched result rows are not persisted.
  • Dialogs and menus remain inside the component that controls their lifecycle.

Page selection sequence

Catalogs loadApp.tsx requests result and input catalogs independently so either side can show its own error.
Context resolvesThe app accepts a URL value only if it appears in the current catalog. Otherwise, it selects the first valid option.
URL stays in syncA replace-state effect records current context without adding history entries for every selection change.
View rendersrenderWorkspace() selects one page and gives it the smallest required context.
Page fetches its dataEffects own AbortController instances so stale responses cannot overwrite newer selections.
Results and comparison charts

ChartCard.tsx requests the primary run and, when selected, the comparison run. Plot.tsx converts result rows into Plotly traces. Difference mode aligns rows by their analytical identity and calculates comparison − primary.

Hourly charts request one year and may send a time range. The server samples only the displayed response; downloads keep the complete source CSV.

Input editing

The browser stores changed cells using the original __row_id, not the visible page index. Filters and pagination therefore cannot redirect an edit to another CSV row. A save includes the last observed file revision; HTTP 409 forces a reload when the file changed externally.

Dashboard persistence

utility.tsx owns the versioned JSON format and DashboardStore abstraction. The local implementation uses localStorage. It converts older definitions when it reads them. New saves and exports use the current schema.

Backend logic

app.py is the transport layer. It validates requests and translates domain errors into HTTP responses. The three domain modules own file semantics.

Read

Catalog and charts

The result catalog walks results/<run>/csvs. The server permits only configured table names and modes. It combines and deduplicates yearly files, and can filter and sample hourly data.

Edit

Inputs and configuration

Input settings determine which tables appear. The UI receives typed CSV values, while saves convert them back to model-compatible text. Round-trip YAML preserves comments and keys that survive an edit.

Execute

Model runs

Only one web-launched run can operate at a time. Each run has a config copy, provenance manifest, state file, log, process group, and temporary directory under logs/web_runs/.

Separate lifecycles. Input scenarios, result runs, and dashboards are different records. A result run does not need the same name as an input scenario. A dashboard stores references to result data, not copies.

Safety and concurrency

Filesystem confinement

  • User-selected path segments resolve below known roots.
  • Result tables must appear in graph_settings.yaml.
  • Hourly/yearly mode must match the chart definition.
  • Resolved result files must remain under the selected sector folder.

Write integrity

  • CSV and YAML writes use a temporary sibling followed by os.replace.
  • File revisions implement optimistic concurrency.
  • A process-local write lock serialises edits.
  • The backend rejects web edits and new scenarios while a web model run is active.

Run integrity

  • Runs do not change the repository-root config.
  • The runner validates the selection and core count before launch.
  • Only one web-launched process can run at a time.
  • Cancellation signals the process group, then escalates after a grace period.

Browser race prevention

  • Context-changing reads use abort signals.
  • Dirty editors prompt before navigation.
  • Stable source row IDs survive filtering and paging.
  • The browser parses and normalises dashboard imports before storage.

Verification

Run checks from the repository root. The Python suite needs the web dependencies available in the selected environment.

npm --prefix pypsa_spice_web/frontend test
npm --prefix pypsa_spice_web/frontend run build
conda run -n hotpot python -m unittest discover -s tests -p 'test*.py' -q
git diff --check -- pypsa_spice_web tests

For frontend changes

Exercise the affected view, URL refresh/back navigation, empty/loading/error states, light and dark themes, and unsaved-change prompts.

For backend changes

Test success plus invalid paths, missing files, stale revisions, active-run locks, and files that differ from the common happy-path schema.
